# Лабораторная работа №2 — Когда индексов недостаточно

Работа выполняется на таблице `events`, которая постепенно наполняется до 10 000, 100 000, 1 000 000 и 5 000 000 строк. Размер 10 000 000 строк можно использовать дополнительно, если хватает ресурсов компьютера.

## Часть A. Анализ роста таблицы

### 1. Подготовка таблицы

Создана таблица `events` с полями `id`, `user_id`, `event_type`, `payload`, `created_at`. Она имитирует поток событий приложения: входы пользователей, сообщения, покупки и прочие действия.

### 2. Наполнение данными

Данные добавляются через `generate_series()`. Для корректного сравнения таблица наполняется поэтапно: 10 000, 100 000, 1 000 000 и 5 000 000 строк. После каждого наполнения выполняется `ANALYZE events`, чтобы PostgreSQL обновил статистику.

### 3. Размер таблицы

Размер таблицы измеряется через `pg_relation_size('events')`, а общий размер вместе с индексами — через `pg_total_relation_size('events')`.

| Количество строк | Размер таблицы | Общий размер с индексами |
|---|---|---|
| 10 000 | 672 kB | 944 kB |
| 100 000 | 6672 kB | 8912 kB |
| 1 000 000 | 65 MB | 87 MB |
| 5 000 000 | 326 MB | 433 MB |

С ростом количества строк увеличивается не только размер таблицы, но и размер индексов. Поэтому даже хорошие индексы становятся дороже в обслуживании.

### 4. SELECT без индекса

Запрос:

```sql
SELECT *
FROM events
WHERE user_id = 123;
```

| Количество строк | Scan | Actual Rows | Rows Removed by Filter | Execution Time |
|---|---|---|---|---|
| 10 000 | Seq Scan | 0 | 10 000 | 0.479 ms |
| 100 000 | Seq Scan | 0 | 100 000 | 4.105 ms |
| 1 000 000 | Parallel Seq Scan | 4 | 333 332 × 3 | 21.562 ms |
| 5 000 000 | Parallel Seq Scan | 41 | 1 666 653 × 3 | 101.817 ms |

Без индекса PostgreSQL вынужден выполнять `Sequential Scan`: он просматривает таблицу целиком и отбрасывает строки, где `user_id` не равен 123. Чем больше таблица, тем больше `Rows Removed by Filter` и тем выше время выполнения.

### 5. Индекс по user_id

Создан индекс:

```sql
CREATE INDEX idx_events_user_id
ON events(user_id);
```

| Количество строк | Scan | Execution Time | Index Cond |
|---|---|---|---|
| 100 000 | Bitmap Heap Scan + Bitmap Index Scan | 0.144 ms | `user_id = 123` |
| 1 000 000 | Bitmap Heap Scan + Bitmap Index Scan | 0.070 ms | `user_id = 123` |
| 5 000 000 | Bitmap Heap Scan + Bitmap Index Scan | 0.291 ms | `user_id = 123` |

1. План меняется с `Sequential Scan` на `Index Scan` или `Bitmap Heap Scan`.
2. Время выполнения уменьшается, потому что PostgreSQL больше не читает всю таблицу.
3. Индекс особенно эффективен при высокой селективности, когда найдено мало строк.
4. При росте таблицы индекс помогает сильнее, но сам индекс тоже занимает место и требует обслуживания.

### 6. Индекс по created_at

Запрос за один день является селективным относительно годового объёма данных:

```sql
SELECT *
FROM events
WHERE created_at >= NOW() - INTERVAL '1 day';
```

Индекс `idx_events_created_at` помогает быстро найти недавние события. Но если диапазон становится широким и возвращает большую часть таблицы, PostgreSQL может снова выбрать `Sequential Scan` или `Bitmap Heap Scan`.

### 7. Сортировка и LIMIT

Для запроса:

```sql
SELECT *
FROM events
WHERE user_id = 123
ORDER BY created_at DESC
LIMIT 100;
```

создан индекс:

```sql
CREATE INDEX idx_events_user_created
ON events(user_id, created_at DESC);
```

1. После создания индекса план должен стать эффективнее.
2. Операция `Sort` может исчезнуть, потому что индекс уже хранит события пользователя в порядке `created_at DESC`.
3. Индекс полезен, потому что одновременно поддерживает фильтрацию по `user_id`, сортировку и `LIMIT`.

### 8. Агрегация

Запрос:

```sql
SELECT event_type, COUNT(*)
FROM events
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY event_type;
```

1. PostgreSQL должен отобрать события за 30 дней и сгруппировать их по `event_type`.
2. Даже при наличии индекса по `created_at` запрос может оставаться дорогим, потому что нужно обработать много строк и выполнить агрегацию.
3. Индекс по `created_at` помогает только на этапе фильтрации.
4. Если данных много, дополнительно могут понадобиться партиционирование, материализованные представления или предварительная агрегация.

### 9. INSERT при наличии индексов

1. Время выполнения `INSERT` увеличивается.
2. Чем больше индексов создано на таблице, тем больше структур PostgreSQL должен обновить при вставке.
3. Индексы ускоряют чтение, но замедляют запись.

Вывод: нельзя создавать индексы только ради возможной пользы для `SELECT`. Нужно учитывать цену `INSERT`, `UPDATE` и `DELETE`.

### 10. Размер индексов

Размер индексов измеряется запросом к `pg_stat_user_indexes` и `pg_relation_size(indexrelid)`.

| Индекс | Размер |
|---|---|
| `idx_events_user_id` | 50 MB |
| `idx_events_created_at` | 107 MB |
| `idx_events_user_created` | 150 MB |

Индексы занимают дополнительное место на диске. С ростом таблицы растут и индексы, поэтому большое количество индексов может стать отдельной проблемой.

### 11. Когда индекс не спасает

Запрос:

```sql
SELECT DATE(created_at), COUNT(*)
FROM events
WHERE created_at >= NOW() - INTERVAL '365 days'
GROUP BY DATE(created_at);
```

1. Запрос может оставаться медленным, потому что он берёт почти всю таблицу за год.
2. Индекс по `created_at` плохо помогает, если условие возвращает большую часть строк.
3. Дополнительно запрос выполняет `GROUP BY DATE(created_at)`, то есть вычисление и агрегацию.
4. Для ускорения лучше использовать партиционирование по дате, материализованное представление или отдельную таблицу дневной статистики.

## Часть B. Анализ таблицы сервиса

### 12. Выбор таблицы

Выбрана таблица `"Bookings"`.

1. Таблица хранит бронирования номеров.
2. Она растёт при каждом новом бронировании.
3. Чаще всего будут использоваться поля `"RoomId"`, `"GuestEmail"`, `"CheckInDate"`, `"CheckOutDate"`, `"Status"`, `"CreatedAt"`.
4. Потенциальная проблема: при большом объёме данных запросы по датам, гостю и последним бронированиям могут начать читать слишком много строк или выполнять дорогую сортировку.

### 13. Три SQL-запроса

Query 1:

```sql
SELECT *
FROM "Bookings"
WHERE "RoomId" = 1;
```

Query 2:

```sql
SELECT *
FROM "Bookings"
WHERE "CheckInDate" >= DATE '2026-01-01'
  AND "CheckInDate" < DATE '2026-02-01';
```

Query 3:

```sql
SELECT *
FROM "Bookings"
WHERE "GuestEmail" = 'guest@example.com'
ORDER BY "CreatedAt" DESC
LIMIT 50;
```

### 14. Baseline

| Query | SQL | Scan | Execution Time | Rows | Проблема |
|---|---|---|---|---|---|
| 1 | Поиск по `"RoomId"` | Index Scan `IX_Bookings_RoomId` | 0.026 ms | 0 | В текущей базе нет тестовых бронирований |
| 2 | Диапазон по `"CheckInDate"` | Index Scan `IX_Bookings_CheckInDate` | 0.034 ms | 0 | В текущей базе нет тестовых бронирований |
| 3 | Гость + сортировка + limit | Index Scan `IX_Bookings_GuestEmail` + Sort | 0.062 ms | 0 | Есть отдельная операция `Sort`; данных для нагрузки нет |

### 15. Рост данных

Запросы нужно проверить на объёмах 100k, 1m и 5m строк. Если с ростом данных время выполнения растёт почти линейно, значит PostgreSQL читает слишком много строк или выполняет дорогую операцию над большим набором данных.

### 16. Сравнение результатов

| Query | Количество строк | Execution Time | Scan |
|---|---|---|---|
| 1 | 100k | 0.061 ms | Bitmap Heap Scan + Bitmap Index Scan |
| 1 | 1m | 0.118 ms | Bitmap Heap Scan + Bitmap Index Scan |
| 2 | 100k | 0.242 ms | Bitmap Heap Scan + Bitmap Index Scan |
| 2 | 1m | 6.470 ms | Bitmap Heap Scan + Bitmap Index Scan |
| 3 | 100k | 0.075 ms | Bitmap Heap Scan + Sort |
| 3 | 1m | 0.068 ms | Bitmap Heap Scan + Sort |

### 17. Анализ проблемы

Проблема считается найденной, если в плане есть `Sequential Scan` на большой таблице, высокая стоимость сортировки, большое значение `Rows Removed by Filter` или большое время выполнения при малом количестве возвращаемых строк.

### 18. Оптимизация

Для Query 3 подходит индекс:

```sql
CREATE INDEX "IX_Bookings_GuestEmail_CreatedAt_Desc"
ON "Bookings" ("GuestEmail", "CreatedAt" DESC);
```

Он помогает найти бронирования конкретного гостя и сразу вернуть их в порядке от новых к старым без отдельной дорогой сортировки.

### 19. Сравнение до и после

До оптимизации запрос мог использовать индекс только по `"GuestEmail"` и затем выполнять `Sort` по `"CreatedAt"`. После создания составного индекса PostgreSQL может читать данные сразу в нужном порядке.

| Показатель | До оптимизации | После оптимизации |
|---|---|---|
| Scan | Index Scan `IX_Bookings_GuestEmail` | Index Scan `IX_Bookings_GuestEmail_CreatedAt_Desc` |
| Sort | Есть `Sort` по `"CreatedAt" DESC` | Нет отдельного `Sort` |
| Execution Time | 0.062 ms | 0.046 ms |
| Rows | 0 | 0 |

## Контрольные вопросы

1. `Seq Scan` становится проблемой, когда таблица большая, а запрос возвращает малую часть строк.
2. PostgreSQL может не использовать индекс, если условие низкоселективное, статистика показывает высокую стоимость индекса или запрос возвращает большую часть таблицы.
3. Каждый индекс замедляет `INSERT`, потому что его нужно обновлять при добавлении строки.
4. Большое количество индексов увеличивает размер базы, замедляет запись и усложняет обслуживание.
5. Составной индекс нужен, когда частый запрос использует несколько колонок вместе.
6. Индекс не помогает при агрегации, если запрос всё равно должен обработать большую часть строк.
7. При росте таблицы с 100k до 5m строк время запросов без подходящего индекса обычно растёт значительно, часто почти линейно.
8. `EXPLAIN ANALYZE` показывает реальный план выполнения, фактическое время и фактическое количество строк.
9. `Rows Removed by Filter` показывает, сколько строк PostgreSQL прочитал, но отбросил из-за условия `WHERE`.
10. `Index Cond` показывает условие, которое реально используется индексом.
11. `Index Scan` чаще подходит для малого числа строк, а `Bitmap Index Scan` — для большего набора строк, который выгоднее читать пачками.
12. Индекс не гарантирует быстрый запрос, если условие возвращает много строк, есть сортировка, агрегация или вычисления над большим объёмом данных.
13. `GROUP BY` может быть дорогим на больших таблицах, потому что PostgreSQL должен сгруппировать большое количество строк.
14. Для аналитических запросов лучше использовать партиционирование, материализованные представления или заранее подготовленные агрегаты.
15. Индекс занимает место на диске и растёт вместе с таблицей.
16. Лишний индекс вреден, если он почти не используется, но замедляет запись и занимает место.
17. Решение о создании индекса PostgreSQL не принимает сам: индекс создаёт разработчик или администратор. PostgreSQL только выбирает, использовать ли уже существующий индекс в конкретном плане.
18. Итоговый вывод: индексы важны, но они не решают все проблемы производительности. Нужно измерять запросы, анализировать планы, учитывать рост данных и выбирать оптимизацию под конкретную нагрузку.
