## Часть 1. RANGE PARTITIONING по дате

Создана таблица:

```sql
CREATE TABLE lab03.events (
    id BIGINT NOT NULL,
    user_id BIGINT NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload TEXT,
    created_at TIMESTAMP NOT NULL
) PARTITION BY RANGE (created_at);
```

Созданы три дневные партиции с интервалами `[2026-09-09, 2026-09-10)`, `[2026-09-10, 2026-09-11)`, `[2026-09-11, 2026-09-12)`. Через `generate_series()` загружено 300 000 событий: по 100 000 в день, `click` — ровно 10% строк. После загрузки выполнен `ANALYZE`.

Проверка фактического размещения:

```sql
SELECT tableoid::regclass AS partition_name, COUNT(*)
FROM lab03.events
GROUP BY tableoid
ORDER BY partition_name;
```

| Партиция | Строк |
|---|---:|
| `events_2026_09_09` | 100 000 |
| `events_2026_09_10` | 100 000 |
| `events_2026_09_11` | 100 000 |

Ответы:

1. `2026-09-10 12:00:00` попадает в `events_2026_09_10`.
2. `2026-09-11 00:00:00` попадает в `events_2026_09_11`.
3. До создания следующей партиции вставка за `2026-09-12` завершилась ошибкой **SQLSTATE 23514**, `no partition of relation "events" found for row`.
4. Для RANGE нижняя граница включается, верхняя исключается. Поэтому соседние диапазоны не пересекаются, а полночь принадлежит следующей партиции. Это правило PostgreSQL, а не особенность точности `TIMESTAMP`. [Документация PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-partitioning.html).

Граничные вставки выполнены внутри транзакции с `ROLLBACK`; они не изменили объём данных для замеров.

## Часть 2. Partition pruning

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*) FROM lab03.events
WHERE created_at >= TIMESTAMP '2026-09-10'
  AND created_at < TIMESTAMP '2026-09-11';
```

В фактическом плане есть только `Seq Scan on events_2026_09_10`: прочитано 100 000 строк одной партиции, время — **30.076 ms**. Партиции за 9 и 11 сентября отсутствуют в дереве выполнения. Это показывает отсечение на этапе планирования. Число рассмотренных планировщиком объектов нельзя отождествлять с числом физически просканированных таблиц; в данном случае реально сканируется одна.

Для второго запроса:

```sql
SELECT COUNT(*) FROM lab03.events WHERE event_type = 'click';
```

план содержит `Parallel Append` и три `Parallel Seq Scan`. Возвращается один результат агрегата; подходящих событий — 30 000. Время — **33.066 ms**. По `event_type` нельзя определить день события, поэтому все три партиции нужны.

Строка `Subplans Removed` не обязана присутствовать: при отсечении во время планирования ненужные дочерние планы уже отсутствуют. Для parallel-узлов `actual rows` нужно читать вместе с `loops`; это не всегда общее число строк запроса.

## Часть 3. RANGE PARTITIONING по числовому значению

Таблица `products` разделена по `price`:

| Партиция | Диапазон | Проверенные цены |
|---|---|---|
| `products_cheap` | `[0, 100)` | 0; 99.99 |
| `products_medium` | `[100, 1000)` | 100; 499.99; 999.99 |
| `products_expensive` | `[1000, MAXVALUE)` | 1000; 5000 |

Условие `price >= 100 AND price < 500` использовало только `Seq Scan on products_medium`, вернуло две строки за **0.027 ms**. Другие диапазоны не пересекаются с условием. Строка с ценой 999.99 находится в нужной партиции, но отбрасывается фильтром: pruning выбирает целую партицию, а не отдельные строки внутри неё.

В определении из методички отрицательные цены не покрыты; без дополнительной партиции такая вставка вызовет ошибку.

## Часть 4. LIST PARTITIONING

`customers` разделена по `customer_type`: `B2C`, `B2B`, `Enterprise`. Запрос `WHERE customer_type = 'B2B'` использовал только `customers_b2b`, вернул одну строку за **0.142 ms**.

Другие партиции не могут содержать значение `B2B` по своим ограничениям. LIST задаёт конкретные значения категорий, RANGE — интервалы упорядоченных значений.

## Часть 5. Неизвестное значение и DEFAULT

Первая вставка `(100, 'Test User', 'VIP')` завершилась ожидаемой ошибкой **23514**. После команды:

```sql
CREATE TABLE lab03.customers_default
PARTITION OF lab03.customers DEFAULT;
```

повторная вставка прошла; `RETURNING tableoid::regclass` показал `customers_default`.

1. DEFAULT принимает значения, не покрытые другими партициями.
2. Она полезна, если новые категории допустимы и их появление не должно немедленно останавливать запись.
3. Без контроля DEFAULT может накопить большую смешанную таблицу и скрыть отсутствие нужных категорий. Перед добавлением отдельной партиции `VIP` существующие VIP-строки потребуется перенести: они не могут оставаться в DEFAULT при новом разбиении.

У `events` DEFAULT намеренно не создана: в эксплуатационном эксперименте отсутствие будущего диапазона должно обнаруживаться явно.

## Часть 6. HASH PARTITIONING

`user_events` разделена по `HASH (user_id)` на четыре партиции с `MODULUS 4` и остатками 0–3. Загружено 100 000 различных `user_id`.

| Партиция | Строк | Доля |
|---|---:|---:|
| `user_events_0` | 25 126 | 25.13% |
| `user_events_1` | 24 978 | 24.98% |
| `user_events_2` | 24 971 | 24.97% |
| `user_events_3` | 24 925 | 24.93% |

1. Распределение близко к равномерному, но не обязано быть точным. Разница максимума и минимума — 201 строка.
2. HASH полезен для распределения большого множества ключей по ограниченному числу частей. Проверка `user_id = 12345` прочитала только `user_events_0`, вернула одну строку за **2.096 ms**.
3. RANGE сохраняет смысл диапазона ключа; HASH распределяет по хешу. Номер партиции не следует вычислять как `user_id % 4`: используется внутренняя хеш-функция PostgreSQL.
4. Старые и новые события одного пользователя попадают в одну HASH-партицию. Для удаления данных старше трёх лет нельзя удалить одну целую такую партицию: потребуется фильтрация по дате во всех частях.

Большое число событий одного «горячего» пользователя всё равно попадёт в одну партицию; HASH не гарантирует равную нагрузку при любом распределении исходных данных.

## Часть 7. Выбор стратегии

| Сценарий | Стратегия | Обоснование |
|---|---|---|
| A. Миллионы событий ежедневно, удаление старше трёх лет | RANGE по дате | Временные интервалы соответствуют сроку хранения. Старые диапазоны можно отсоединять или удалять целиком. |
| B. Пользователи B2C/B2B/Enterprise | LIST по типу | Запросы используют конкретные категории, поэтому могут обращаться к одной соответствующей части. |
| C. Распределение по `user_id` | HASH | Хеширование множества пользователей даёт примерно равномерное распределение по фиксированному числу разделов. |
| D. Аналитика заказов по `created_at` | RANGE по `created_at` | Диапазон дат позволяет исключить партиции за остальные периоды. |
| E. Платежи EE/LV/LT/FI/SE | LIST по стране | Страна — дискретная категория; значения можно выделять по одному или объединять в группы. |

## Часть 8. Партиционирование и индексы

Проверен запрос с датой и `user_id = 12345`, затем создан `idx_events_user_id` на родительской таблице.

| Состояние | План внутри выбранной партиции | Строк | Execution Time |
|---|---|---:|---:|
| До индекса | `Seq Scan on events_2026_09_10` | 1 | 14.094 ms |
| После индекса | `Index Scan using events_2026_09_10_user_id_idx` | 1 | 0.144 ms |

В обоих случаях дата исключила партиции за 9 и 11 сентября. До индекса PostgreSQL искал одну строку среди 100 000 событий оставшегося дня; после — использовал индексное условие `user_id = 12345`.

`pg_partition_tree('lab03.idx_events_user_id')` показал родительский индекс и три дочерних. Данные индексов физически находятся на партициях; индекс родителя связывает их структуру. Новые партиции, созданные job, также получают соответствующие индексы. [Индексы партиционированных таблиц в PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE).

Комбинация полезна, потому что дата уменьшает число таблиц, а индекс уменьшает объём поиска внутри оставшихся.

## Часть 9. Когда партиционирование не помогает

Для `COUNT(*) WHERE event_type = 'click'` создан индекс `idx_events_event_type`. После создания выполнен `VACUUM (ANALYZE)`, чтобы также обновить карту видимости.

| Состояние | План | Партиций | Подходящих событий | Execution Time |
|---|---|---:|---:|---:|
| До | `Parallel Append` + `Parallel Seq Scan` | 3 | 30 000 | 24.257 ms |
| Индекс + VACUUM | `Append` + `Index Only Scan` | 3 | 30 000 | 5.613 ms |

В каждом `Index Only Scan` зафиксировано `Heap Fetches: 0`. Ускорение связано с индексом и доступностью данных без обращений к heap после VACUUM; это не чистый эксперимент только с добавлением индекса.

Pruning по дате так и не появился: `click` встречается во всех днях. Партиционирование определяет, **какие части таблицы нужны**, а индекс — **как найти данные внутри этих частей**. При более частом значении события планировщик может предпочесть последовательное чтение.

## Часть 10. Автоматическое создание партиций через pg_cron

`pg_cron` — расширение PostgreSQL, которое запускает SQL по расписанию внутри базы. Оно включено через `shared_preload_libraries`, затем миграция выполняет `CREATE EXTENSION pg_cron`. Используются фоновые workers (`cron.use_background_workers=on`), база `hotelbooking`, часовой пояс UTC. [Документация pg_cron](https://github.com/citusdata/pg_cron/tree/v1.6.7).

Собран исходный выпуск `v1.6.7`; в `pg_extension.extversion` он отображает версию SQL-схемы **1.6**. Это разные обозначения версий, а не ошибка установки.

За создание отвечает SQL-функция `lab03.create_partitions_job`. Она вычисляет диапазоны, проверяет имя, родителя и точные границы, создаёт только недостающее и использует транзакционную advisory lock. Горизонт событий: сегодня **и ещё три дня**, всего четыре партиции; для бронирований — текущий месяц и три следующих. Повторный вызов возвращает `created = []`.

`lab03.run_partition_task` вызывает создание либо проверку с текущей датой UTC и записывает JSON-результат в `lab03.partition_job_runs`. Настройки формата дат и времени заданы внутри функции, поэтому они не зависят от настроек pgAdmin.

### Четыре задания

| Имя | Расписание | Назначение |
|---|---|---|
| `lab03-create-events` | `0 1 * * *` | Создать недостающие дневные партиции в 01:00 UTC |
| `lab03-create-bookings` | `0 1 * * *` | Создать недостающие месячные партиции в 01:00 UTC |
| `lab03-check-events` | `*/5 * * * *` | Проверить дневной горизонт каждые пять минут |
| `lab03-check-bookings` | `*/5 * * * *` | Проверить месячный горизонт каждые пять минут |

Пример регистрации из миграции:

```sql
SELECT cron.schedule(
    'lab03-create-events',
    '0 1 * * *',
    $$SELECT lab03.run_partition_task('create', 'events');$$
);
SELECT cron.schedule(
    'lab03-check-events',
    '*/5 * * * *',
    $$SELECT lab03.run_partition_task('check', 'events');$$
);
```

При первом применении миграции горизонт создаётся сразу. Далее расписание хранится в БД и работает, пока запущен PostgreSQL. Прежние Python-циклы `run-job` и `run-check` удалены. Повторный вызов `lab03.schedule_partition_jobs()` регистрирует те же имена без дубликатов. После выключения PostgreSQL пропущенный ночной запуск не следует считать выполненным: проверка обнаружит неполный горизонт, создание можно выполнить вручную или дождаться следующего запуска.

### Как показать работу планировщика

```sql
SELECT jobid, jobname, schedule, active, command
FROM cron.job WHERE jobname LIKE 'lab03-%' ORDER BY jobid;

SELECT j.jobname, d.status, d.return_message, d.start_time, d.end_time
FROM cron.job_run_details d JOIN cron.job j USING (jobid)
WHERE j.jobname LIKE 'lab03-%'
ORDER BY d.runid DESC LIMIT 20;

SELECT task, target, result, finished_at
FROM lab03.partition_job_runs ORDER BY id DESC LIMIT 20;
```

`cron.job_run_details` показывает технический результат SQL. **`succeeded` не означает, что партиции исправны**: успешно выполненная проверка может вернуть CRITICAL. Предметное состояние хранится в `partition_job_runs.result` и `partition_health_state`. При SQL-ошибке смотреть `failed` и `return_message`. Истории запусков автоматически не очищаются; на длительно работающем стенде для них нужно выбрать срок хранения.

## Часть 11. Сбой job, уведомление и восстановление

Создание и проверка зарегистрированы как отдельные задания. Если выключить `lab03-create-events`, `lab03-check-events` продолжает работать. Проверка сверяет весь требуемый горизонт, включая связь с родителем и границы; отсоединённая или неправильно определённая партиция также даёт CRITICAL.

Состояние хранится в `partition_health_state`, сообщения — в `partition_alert_outbox`. Переход в CRITICAL формирует alert, неизменившиеся статус и список проблем не создают повторов. Изменившийся список формирует новое сообщение. CRITICAL → OK формирует recovery; первый здоровый запуск уведомление не отправляет.

### Доставка уведомления

pg_cron запускает SQL-проверку, которая помещает уведомление в очередь. Python только доставляет сообщения из этой очереди по HTTP; он не запускает регулярное создание или проверку партиций. Для отдельного наблюдения в двух терминалах:

```powershell
python docs/lab-03/partition_jobs.py serve --output docs/lab-03/results/received-alerts.jsonl
```

```powershell
python docs/lab-03/partition_jobs.py run-dispatch --webhook http://127.0.0.1:8787/alerts
```

Получатель — локальный HTTP webhook, вариант «другой канал» из методички. Сообщение содержит таблицу, статус, список отсутствующих партиций, горизонт с единицей измерения и время проверки UTC. Получение POST подтверждается HTTP 204 и записью `alert_received`. Без dispatcher проверка продолжает работать, а уведомления остаются в очереди до доставки.

При HTTP-ошибке `delivered_at` остаётся пустым, dispatcher повторяет доставку при следующем опросе. Гарантия — at-least-once: после падения между получением POST и записью `delivered_at` запрос может повториться. `event_id` и `Idempotency-Key` позволяют получателю подавлять такие повторы. Нужен один экземпляр dispatcher; режим `serve --output` восстанавливает обработанные идентификаторы из журнала после перезапуска.

### Демонстрация именно через pg_cron

```powershell
python docs/lab-03/partition_jobs.py demo
```

Команда использует **фактическую текущую дату**, поэтому `--today` здесь не принимается. Python подготавливает сбой и ожидает результаты в БД; обнаружение и штатное восстановление выполняют фоновые задания pg_cron.

| Шаг | Что происходит |
|---|---|
| Подготовка | Сохранить расписания и active, создать исходный полный горизонт |
| Искусственный сбой | Выключить создание, удалить только проверенную пустую будущую партицию |
| Контроль | Временно запустить check каждые 2 секунды; дождаться CRITICAL в журнале |
| Повторная проверка | Дождаться ещё одного запуска pg_cron и убедиться, что в очереди один alert |
| Отказ канала | Для events приёмник возвращает 503; сообщение должно остаться недоставленным |
| Доставка | Повторить POST, получить один CRITICAL |
| Восстановление | Включить create каждые 2 секунды; дождаться создания партиции заданием pg_cron |
| Recovery | Дождаться очередного check с OK, доставить recovery |
| Повторный OK | Убедиться, что дубли не появились |
| Завершение | Сохранить историю `cron.job_run_details`, вернуть исходные расписания и active |

Сценарий выполняется для `events` и `Bookings`. Он отказывается удалять непустую партицию. В `finally` предусмотрены восстановление горизонта и возврат настроек заданий при ошибке демонстрации. Для защиты следует запускать один экземпляр demo, без параллельного наполнения стенда и отдельного dispatcher.

Доказательства фоновых запусков сохраняются в [pg-cron-demo.jsonl](lab-03/results/pg-cron-demo.jsonl): `cron_detected_failure`, `cron_restored_partition`, `cron_detected_recovery`, `cron_history`, а также фактические `alert_received`. Результат считается успешным только при двух сообщениях на таблицу — CRITICAL и OK — и успешных завершённых запусках pg_cron.

**Фактический прогон 13 сентября 2026 года:** удалялись пустые `events_2026_09_16` и `bookings_2026_12`. История содержит 12 фоновых запусков со статусом `succeeded`; для каждой таблицы получены один CRITICAL и один recovery, дублей нет. После намеренного HTTP 503 уведомление осталось в очереди и было доставлено повторной попыткой. В конце все четыре задания активны, штатные расписания восстановлены.

Отключение или недоступность всего PostgreSQL останавливает и pg_cron; для контроля такого отказа нужен отдельный внешний монитор. Здесь проверяется отказ задания создания при продолжающей работать БД.

## Часть 12. Партиционирование таблицы HotelBooking

### Выбор таблицы, ключа и стратегии

Выбрана `"Bookings"`: она растёт с каждым бронированием. Ключ — **`"CheckInDate"`**, стратегия — **RANGE по месяцам**. В `BookingReportRepository.GetBookingStatisticsAsync` аналитика фильтрует именно даты заезда, поэтому этот ключ полезнее `CreatedAt` для существующего запроса. Месячный шаг соответствует месячной отчётности и создаёт меньше объектов, чем дневной.

В `lab03."Bookings"` сохранены поля исходной таблицы, связь с лабораторной `"Rooms"` и аналогичные вторичные индексы. Создана обычная `lab03.bookings_baseline` с теми же 300 000 строками и индексами по тем же полям. Все идентификаторы и данные сгенерированы специально для работы.

|---|---|---:|
| `bookings_2026_09` | `[2026-09-01, 2026-10-01)` | 98 901 |

Размер с индексами — **55 MB** для суммы трёх партиций, **52 MB** для baseline. Размер одного родителя не отражает данные партиций, поэтому использован `pg_partition_tree` с суммированием листьев.

### Три запроса из репозиториев

Q1 и Q2 воспроизводят SQL-условия `BookingRepository.GetByIdAsync` и `GetByRoomIdAsync`. Загрузка навигационных объектов через EF `Include` в измерение этих двух запросов не включена. Q3 воспроизводит агрегат `BookingReportRepository.GetBookingStatisticsAsync`, включая JOIN с номерами и условие по отелю. Это измерения SQL, а не времени HTTP endpoint.

```sql
-- Q1: получить бронирование.
SELECT * FROM lab03."Bookings" WHERE "Id" = 12345;

-- Q2: бронирования номера.
SELECT * FROM lab03."Bookings" WHERE "RoomId" = 1;

-- Q3: статистика отеля за октябрь (полный агрегат — в SQL-сценарии).
SELECT COUNT(*), SUM(b."TotalPrice")
FROM lab03."Bookings" b
JOIN lab03."Rooms" r ON b."RoomId" = r."Id"
WHERE r."HotelId" = 1
  AND b."CheckInDate" >= DATE '2026-10-01'
  AND b."CheckInDate" <= DATE '2026-10-31';
```

| Запрос | Baseline | После партиционирования | Pruning | Возвращено строк |
|---|---|---|---|---:|
| Q1, `Id` | `Index Scan`, 0.037 ms | `Append` + 3 `Index Scan`, 0.075 ms | Нет, 3 партиции | 1 |
| Q2, `RoomId` | `Bitmap Heap Scan`, 0.671 ms | `Append` + 3 `Bitmap Heap Scan`, 0.621 ms | Нет, 3 партиции | 300 |
| Q3, статистика октября | `Parallel Seq Scan` + `Hash Join`, 22.979 ms | `Seq Scan` октября + `Hash Join`, 22.492 ms | Да, 1 из 3 | 1 агрегат |

Q3 обработал 102 198 бронирований октября; после JOIN с отелем осталось 10 219. Доступы к буферам на верхнем узле плана снизились с `shared hit=4807 read=3` до `shared hit=1583`. Это число обращений к буферам, не число уникальных физических чтений с диска.

Для Q1 партиционирование даже добавило работу: без даты нужно проверить три индекса. Q2 также не использует pruning; небольшая разница времени не доказывает ускорение от разбиения. Для Q3 объём просматриваемых данных сократился, но большого ускорения на этом объёме не получилось: baseline использовал параллелизм, а план одной партиции был последовательным.

Все времена — **один фактический прогон**, без принудительной очистки кеша. Индексы создавались и данные читались последовательно, поэтому условия кеширования различаются. Для количественного вывода об устойчивом ускорении нужны повторные серии; текущие результаты надёжнее показывают различия структуры планов и pruning.

### Автоматизация и контроль

Для месячной таблицы вызов `create_partitions_job('Bookings', DATE '2026-09-11', 3)` добавил декабрьскую партицию. Миграция 015 регистрирует отдельные задания создания и контроля обеих таблиц. Для `Bookings` демонстрация выключает создание, удаляет пустую крайнюю будущую месячную партицию, ожидает CRITICAL, затем включает создание через pg_cron и ожидает recovery.

В шаге 7 реализована указанная для временных данных ветка задания — создание будущих партиций. Автоматическое удаление исторических бронирований не включено: в проекте не задан срок хранения, а по дате заезда нельзя без дополнительных правил решить, что все связанные данные больше не нужны. Для фиксированного срока хранения можно автоматизировать отсоединение полностью устаревших диапазонов после проверки бизнес-ограничений.

Горизонт три месяца — параметр лабораторной. Для рабочего бронирования его нужно согласовать с максимальной разрешённой датой заезда: бронь за пределами подготовленного горизонта иначе завершится ошибкой.

### Ограничение первичного ключа и перенос в рабочий сервис

В PostgreSQL 16 первичный или уникальный ключ партиционированного родителя должен включать все колонки ключа партиционирования. Поэтому на стенде используется `PRIMARY KEY ("Id", "CheckInDate")`. Он не обеспечивает глобальную уникальность одного `Id` между месяцами. [Ограничения PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-partitioning.html#DDL-PARTITIONING-DECLARATIVE-LIMITATIONS).

Сейчас EF Core настроен на `HasKey(e => e.Id)`, а методы поиска и изменения принимают один `Id`. Поэтому простая подмена `public."Bookings"` учебной таблицей была бы некорректной. Для реального перехода нужны отдельная миграция данных, решение об идентификаторах и внешних ссылках, согласование ключа EF и операций обновления/удаления, создание всех исторических и допустимых будущих диапазонов. Данная работа демонстрирует применение структуры и SQL сервиса в изолированной схеме, а не завершённую миграцию API.

## Контрольные вопросы

1. **Что такое partitioning?** Разделение одной логической таблицы на физические части с правилами распределения строк.
2. **Чем отличается от индекса?** Партиционирование меняет размещение данных и позволяет исключать части таблицы; индекс даёт способ находить строки внутри таблицы или партиции.
3. **Какие стратегии поддерживаются?** Встроенные декларативные RANGE, LIST и HASH.
4. **Когда использовать RANGE?** Когда данные и запросы естественно разделяются по диапазонам, например по датам или ценам.
5. **Когда использовать LIST?** Для дискретных категорий: тип клиента, страна, регион.
6. **Когда использовать HASH?** Для распределения множества значений ключа по фиксированному числу частей, особенно при запросах по равенству этого ключа.
7. **Как выбрать partition key?** Сопоставить частые фильтры, распределение данных и жизненный цикл хранения. В этой работе выбран ключ даты заезда, потому что его использует отчёт сервиса.
8. **Что такое partition pruning?** Исключение партиций, которые заведомо не содержат строки, удовлетворяющие условию запроса.
9. **Почему pruning может не сработать?** Нет ограничения по ключу, диапазон покрывает все части, условие записано через выражение, которое планировщик не может сопоставить границам, либо pruning отключён. Параметры запроса сами по себе не означают невозможность pruning: отсечение бывает и во время выполнения.
10. **Можно ли использовать индексы вместе с partitioning?** Да; в работе индекс по пользователю ускорил поиск внутри одного выбранного дня.
11. **Что произойдёт без подходящей партиции?** При наличии подходящей DEFAULT строка попадёт туда; без неё INSERT завершится ошибкой.
12. **Зачем создавать будущие партиции заранее?** Чтобы смена даты или появление будущей записи не останавливали INSERT и был запас времени на исправление сбоев.
13. **Почему создание нужно автоматизировать?** Диапазоны появляются регулярно; ручное обслуживание легко пропустить, особенно для нескольких таблиц.
14. **Чем логирование отличается от alerting?** Лог сохраняет факт для последующего просмотра; alert активно доставляет сообщение получателю. В стенде доставку подтверждает HTTP-приёмник.
15. **Что такое recovery alert?** Сообщение о переходе из проблемного состояния обратно в OK после восстановления партиций.
16. **Почему нельзя бесконечно повторять одинаковый alert?** Повторы засоряют канал и мешают замечать новые проблемы. Здесь сообщение формируется при изменении состояния или списка отсутствующих партиций.
17. **Всегда ли partitioning ускоряет запросы?** Нет. Поиск бронирования только по Id проверил три индекса и стал медленнее в измеренном прогоне.
18. **Какие проблемы даёт неправильный размер партиций?** Слишком мелкие создают много таблиц и индексов, увеличивают планирование и обслуживание; слишком крупные оставляют большой объём чтения и уменьшают точность удаления по сроку хранения.

Эксперименты показали отсечение партиций при фильтрации по ключу, маршрутизацию RANGE/LIST/HASH и пользу локальных индексов.
