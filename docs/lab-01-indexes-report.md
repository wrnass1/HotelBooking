# Лабораторная работа №1 — EXPLAIN ANALYZE

После запуска сценарий использует `orders` с 1 000 000 строк.

| Запрос | План до индекса | План после индекса | Execution Time |
|---|---|---|---|
| `user_id = 123` |Parallel Seq Scan |Index Scan |106,894 -> 0,309 |
| диапазон `created_at` | Seq Scan| Index Scan| 54,411 -> 8,957|
| `user_id + status` | Bitmap/Index Scan |Index Scan | 0,622 -> 0,684 |
| `WHERE + ORDER BY + LIMIT` |Bitmap + Sort | Index Scan | 1,435 -> 0,282 |

| Метрика | До | После |
|---|---|---|
| Тип Scan | `Parallel Seq Scan` | `Index Scan` |
| Execution Time | `106,894 ms` | `0,309 ms` |
| Actual Rows | `14` | `14` |
| Используемый индекс | нет | `idx_orders_user_id` |


## Ответы по частям методички

### Часть 1. Подготовка таблицы

В лабораторной создана таблица `orders` с полями `id`, `user_id`, `product_id`, `status`, `amount`, `created_at`, `updated_at`. В неё добавляется 1 000 000 строк тестовых данных через `generate_series(1, 1000000)`, после чего выполняется `ANALYZE orders`, чтобы PostgreSQL обновил статистику по таблице.

### Часть 2. EXPLAIN и EXPLAIN ANALYZE

1. PostgreSQL выбрал текущий план выполнения на основе статистики таблицы: количества строк, распределения значений, доступных индексов и расчётной стоимости разных способов чтения.
2. В `EXPLAIN` показывается предполагаемый план без реального выполнения запроса. В `EXPLAIN ANALYZE` запрос действительно выполняется, поэтому там есть фактическое время, фактическое количество строк и расхождение между оценкой и реальностью.
3. `EXPLAIN ANALYZE` даёт больше информации, потому что показывает не только прогноз PostgreSQL, но и реальный результат выполнения.
4. Оценочные строки (`rows`) и фактические строки (`actual rows`) отличаются, потому что планировщик строит прогноз по статистике, а не по полному предварительному чтению таблицы.

### Часть 3. Sequential Scan

1. В запросах `SELECT * FROM orders` и `WHERE amount > 0` используется `Sequential Scan`.
2. PostgreSQL выбирает `Sequential Scan`, когда нужно прочитать всю таблицу или большую часть строк. В таком случае последовательное чтение страниц дешевле множества обращений через индекс.
3. `Sequential Scan` не всегда является плохим решением. Для маленькой таблицы, полного чтения или низкоселективного условия это может быть самый быстрый план.

### Часть 4. B-tree индекс

1. После создания `idx_orders_user_id` план для `WHERE user_id = 123` обычно меняется с `Seq Scan` на индексный план.
2. PostgreSQL использует созданный индекс, потому что `user_id = 123` возвращает небольшую часть таблицы, а B-tree хорошо подходит для поиска по равенству.
3. Время выполнения уменьшается: в моих замерах было `106,894 ms -> 0,309 ms`.

### Часть 5. Индекс по полю status

1. PostgreSQL использует индекс не во всех случаях.
2. Он может выбрать `Sequential Scan`, несмотря на наличие индекса, потому что статусов всего четыре и каждый статус возвращает примерно 25% таблицы. Для такого количества строк чтение через индекс может быть дороже.
3. Чем больше строк возвращает условие, тем меньше польза от индекса. Для малого числа строк вероятнее `Index Scan`, для большого числа строк вероятнее `Sequential Scan` или `Bitmap Heap Scan`.

### Часть 6. Селективность

Селективность — это доля строк, удовлетворяющих условию. Высокая селективность означает, что найдено мало строк: индекс эффективен. Низкая селективность означает, что подходит большая часть таблицы: PostgreSQL часто выбирает `Sequential Scan`, потому что индексные обращения не дают выигрыша.

### Часть 7. Range Query

1. PostgreSQL может использовать разные планы для разных диапазонов дат: для короткого диапазона обычно выгоден индекс, для длинного диапазона может быть выбран `Sequential Scan` или `Bitmap Heap Scan`.
2. Индекс `idx_orders_created_at` лучше всего подходит для коротких диапазонов, например за 1 день или 7 дней, потому что возвращается малая часть таблицы.
3. Для диапазона за 1 год индекс может быть менее эффективен, потому что запрос возвращает слишком много строк. Это показывает, что наличие индекса не гарантирует его использование.

### Часть 8. Bitmap Scan

1. `Bitmap Index Scan` читает индекс и строит битовую карту строк, которые подходят под условие запроса. На этом этапе PostgreSQL ещё не читает сами строки таблицы.
2. `Bitmap Heap Scan` использует битовую карту из предыдущего шага и читает нужные страницы таблицы.
3. PostgreSQL может выбрать `Bitmap Scan` вместо обычного `Index Scan`, когда подходящих строк достаточно много. Тогда выгоднее сначала собрать список нужных строк через индекс, а потом читать страницы таблицы пачками.

### Часть 9. Несколько отдельных индексов

1. PostgreSQL может использовать как один индекс, так и несколько индексов.
2. В плане для `WHERE user_id = 123 AND status = 'PAID'` при отдельных индексах по `user_id` и `status` может появиться `BitmapAnd`.
3. PostgreSQL объединяет результаты нескольких индексов, когда каждый индекс покрывает отдельное условие, а вместе они дают более точный набор строк.

### Часть 10. Composite Index

1. Составной индекс не всегда лучше нескольких отдельных индексов.
2. Он лучше для конкретного запроса, если условия идут по его колонкам, например `user_id` и `status`.
3. Выбор между отдельными индексами и одним составным зависит от частоты запросов, селективности условий, порядка колонок и стоимости поддержки индексов при изменении данных.

### Часть 11. Порядок колонок в составном индексе

1. Порядок колонок влияет на возможность использования индекса. В B-tree индексе особенно важна первая колонка.
2. `(user_id, created_at)` и `(created_at, user_id)` — разные индексы, потому что данные в них отсортированы в разном порядке.
3. Для запроса `WHERE user_id = 123 AND created_at > ...` лучше подходит `(user_id, created_at)`. Для запроса только по дате лучше подходит индекс, который начинается с `created_at`.

### Часть 12. WHERE + ORDER BY

1. Операция `Sort` должна исчезнуть или стать ненужной после создания индекса `(user_id, created_at DESC)`.
2. Индекс может использоваться для сортировки, потому что B-tree хранит значения в отсортированном порядке.
3. Порядок колонок важен: сначала запрос фильтрует по `user_id`, затем сортирует найденные строки по `created_at DESC`.

### Часть 13. API-паттерн Pagination Query

1. План до оптимизации нужно сохранить из `EXPLAIN (ANALYZE, BUFFERS)` для запроса с `WHERE user_id = 123 ORDER BY created_at DESC LIMIT 20`.
2. Подходящий индекс: `idx_orders_user_created_at_desc` на `(user_id, created_at DESC)`.
3. После создания индекса нужно повторно выполнить `EXPLAIN ANALYZE`.
4. После оптимизации план должен читать строки сразу в нужном порядке по индексу.
5. Время выполнения сравнивается по строке `Execution Time` до и после оптимизации.
6. Индекс выбран так, чтобы одновременно поддержать фильтрацию по пользователю, сортировку по дате и ограничение `LIMIT`.

### Часть 14. Index Only Scan

1. `Index Only Scan` отличается от обычного `Index Scan` тем, что PostgreSQL может получить все нужные данные из индекса.
2. PostgreSQL может не обращаться к основной таблице, если все колонки из `SELECT` и `WHERE` есть в индексе, а visibility map показывает, что строки видимы текущей транзакции.
3. Для `Index Only Scan` нужны подходящий покрывающий индекс, наличие всех нужных полей в индексе или в `INCLUDE`, актуальная статистика и достаточно обновлённая visibility map после `VACUUM`.

### Часть 15. Partial Index

1. Преимущество `partial index` в том, что он хранит не все строки таблицы, а только строки, подходящие под условие.
2. `Partial index` полезен для частых запросов по ограниченной части данных, например только по статусу `NEW`.
3. Один `partial index` нельзя использовать для всех типов запросов, потому что он содержит только часть строк. Если запрос не включает условие partial index, PostgreSQL не может гарантировать, что в индексе есть все нужные данные.

### Часть 16. Expression Index

Expression index нужен, когда запрос фильтрует не по самому значению колонки, а по выражению. Например, обычный индекс по `email` не подходит для `WHERE LOWER(email) = 'test@example.com'`, потому что в запросе используется `LOWER(email)`. Для такого запроса нужен индекс `idx_users_lower_email` на выражение `LOWER(email)`.

### Часть 17. Влияние индексов на INSERT

1. Время выполнения `INSERT` после добавления индексов обычно увеличивается.
2. Это происходит потому, что PostgreSQL должен добавить новую строку не только в таблицу, но и во все подходящие индексы.
3. При добавлении новой строки PostgreSQL обновляет каждый индекс этой таблицы: вычисляет индексируемые значения и вставляет ссылки на новую строку в индексные структуры.

### Часть 18. Статистика использования индексов

1. Чаще всего использовались те индексы, у которых больше значение `idx_scan` в `pg_stat_user_indexes`.
2. Индексы с `idx_scan = 0` в статистике на момент проверки не использовались.
3. Индекс с `idx_scan = 0` нельзя автоматически считать бесполезным. Он мог быть создан недавно, использоваться редко или быть важным для редкого отчёта.
4. При удалении индекса есть риск замедлить редкие, но важные запросы, потерять индекс для уникальности или увеличить время восстановления производительности, если индекс понадобится снова.

### Часть 19. Оптимизация сложного запроса

1. Для сложного запроса сначала выполняется `EXPLAIN ANALYZE`.
2. Проблема без подходящего индекса: PostgreSQL может читать и сортировать лишние строки.
3. Подходящий индекс: `CREATE INDEX idx_orders_user_status_created_at_desc ON orders(user_id, status, created_at DESC);`.
4. Поля `user_id` и `status` стоят первыми, потому что по ним используется равенство. Поле `created_at DESC` стоит последним, потому что по нему есть диапазон и сортировка.
5. После создания индекса запрос измеряется повторно.
6. Время выполнения сравнивается по `Execution Time`, а план — по типу сканирования, количеству прочитанных строк и наличию операции `Sort`.

### Часть 20. Выбор растущей сущности

1. Название таблицы: `orders`.
2. Сущность отвечает за заказы пользователей: хранит пользователя, товар, статус, сумму и даты создания/обновления.
3. Эта таблица будет расти быстрее остальных, потому что каждый новый заказ создаёт новую строку, а старые заказы обычно нельзя удалять из-за истории и аналитики.
4. Потенциальный объём через год: от 1 000 000 строк и выше.
5. Чаще всего для поиска и фильтрации используются `user_id`, `status`, `created_at`, а также комбинации `user_id + status` и `user_id + created_at`.

### Часть 21. Анализ трёх запросов

1. Проблема с производительностью есть там, где PostgreSQL читает слишком большую часть таблицы или выполняет сортировку большого результата.
2. `Sequential Scan` допустим только если условие возвращает большую часть таблицы. Для селективных запросов по `user_id` он является признаком потенциальной проблемы.
3. Запрос по `user_id` селективен. Запрос по `status` низкоселективен. Запрос с несколькими условиями обычно более селективен, чем каждое условие отдельно.
4. Для запроса по `user_id` подходит индекс `idx_orders_user_id`. Для запроса с несколькими фильтрами лучше подходит составной индекс. Для `WHERE + ORDER BY + LIMIT` нужен индекс, который совпадает с фильтрами и порядком сортировки.
5. Существующий индекс можно улучшить, если заменить несколько отдельных индексов на составной индекс под частый запрос.
6. SQL-запрос можно улучшить, если убрать лишние поля из `SELECT`, добавить более точные условия или заменить неиндексируемое выражение на индексируемое.

### Часть 22. Выбор запроса для оптимизации

Для оптимизации выбран запрос:

```sql
SELECT id, amount, status, created_at
FROM orders
WHERE user_id = 123
  AND status = 'PAID'
  AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC
LIMIT 50;
```

Проблема: без подходящего составного индекса PostgreSQL может читать и сортировать лишние строки. Измерение выполняется через `EXPLAIN (ANALYZE, BUFFERS)`. После анализа создаётся индекс `idx_orders_user_status_created_at_desc`, затем запрос измеряется повторно. Результат сравнивается по типу сканирования, наличию `Sort`, количеству прочитанных строк и `Execution Time`.

### Часть 23. Итоговый вопрос

Нельзя индексировать всё, потому что каждый индекс занимает место на диске, замедляет `INSERT`, `UPDATE` и `DELETE`, усложняет выбор плана для PostgreSQL и требует обслуживания. Индекс должен создаваться под реальные частые или дорогие запросы, а не просто на каждую колонку.

## Вывод

В ходе лабораторной работы была создана таблица `orders` с большим объёмом тестовых данных — 1 000 000 строк. На этой таблице были исследованы разные планы выполнения запросов в PostgreSQL: `Sequential Scan`, `Index Scan`, `Bitmap Index Scan`, `Bitmap Heap Scan` и `Index Only Scan`.

По результатам работы видно, что индекс ускоряет запросы не всегда, а только тогда, когда условие достаточно селективно и возвращает небольшую часть таблицы. Для поиска по `user_id` B-tree индекс значительно уменьшил время выполнения запроса. При фильтрации по `status` индекс оказался менее полезным, потому что каждый статус встречается часто и возвращает большую часть строк.

Также было показано, что порядок колонок в составном индексе влияет на его эффективность. Индекс `(user_id, created_at)` и индекс `(created_at, user_id)` подходят для разных запросов, потому что PostgreSQL эффективно использует начало индекса. Для запросов с `WHERE`, `ORDER BY` и `LIMIT` наиболее полезны индексы, которые одновременно поддерживают фильтрацию и сортировку.

В результате можно сделать вывод, что индексы нужно проектировать под реальные запросы приложения. Перед созданием индекса необходимо смотреть `EXPLAIN ANALYZE`, сравнивать планы до и после оптимизации, учитывать селективность условий и помнить, что лишние индексы замедляют изменение данных и занимают место на диске.
